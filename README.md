# 弈境（原生 Android）

“**弈境**”是一款可直接导入 Android Studio 的原生 Android Kotlin 五子棋项目。应用使用 Jetpack Compose 绘制棋盘和界面，所有人机对局规则与 AI 计算均在设备本地完成；局域网对战则仅在同一可互通 Wi‑Fi 中建立直连。

## 已实现的体验与功能

应用提供 15×15 自由规则的五子棋对局、星位、末手标记、回合状态、AI 搜索节点/完成深度展示，以及新手、普通、困难、大师四档难度。人机模式打开后停留在开始页，用户可选择难度与先手规则，并点击“开始对局”后才会开局；先手规则支持随机先手、我先手和 AI 先手。局内提供暂停/继续和结束对局操作。应用已接入一枚深海蓝、木棋盘与黑白棋子主题的启动图标，并同时提供圆形图标资源。

棋盘触控采用“**最近交叉点映射**”：点击任意棋盘交叉点附近时，坐标会四舍五入到最近格点后再校验有效范围。这修复了原先以截断取整处理触控坐标时，在每个格点右侧区域可能被错误归类或忽略、导致“点了不落子”的问题。

| 功能 | 当前实现 |
|---|---|
| 平台与界面 | Kotlin、Jetpack Compose、竖屏原生 Android UI、多密度启动图标 |
| 对局规则 | 15×15 自由规则，连成五子或以上获胜 |
| 人机分工 | 本地 AI；开始页可选随机先手、我先手或 AI 先手 |
| AI 战术底线 | NDK 一手成五/必防扫描、断四补杀/封堵、扩展 VCF、受控 VCT 证明树搜索 |
| AI 主搜索 | 轻量开局库、候选点局部化与缓存、模式码缓存、PVS、killer/history 启发、带上下界语义的 Zobrist 置换表 |
| AI 验证 | 可版本化的固定残局基准、等价最佳着集合与单题时间保护 |
| 难度控制 | 搜索时限、最大深度、候选点宽度和低档随机性 |
| 流畅性 | AI 在后台线程计算，主线程保持棋盘动画与触控响应 |
| 对局流程 | 开始页显式开局、先手规则选择、暂停/继续、结束对局、结果提示 |

> 本版本是“强实用 AI”而非竞赛级神经网络引擎。它以移动端离线性能与可维护性为优先，适合首版上线和后续继续演进。

## AI 设计

AI 的前两手由轻量中心化开局库处理：首手抢占中心，中心开局后的应手和第三手采用对称布局；之后立即交回搜索，避免开局库压制局面特有的防守需求。每次搜索先使用 NDK/C++ 内核扫描己方一手成五和对手一手成五的必防点；JNI 库若因 ABI、加载或调用异常而不可用，会自动回退到语义等价的 Kotlin 扫描。它能够识别并补全/封堵断四，并在困难与大师档尝试扩展 VCF（连续冲四）强迫威胁搜索。困难档最多验证三层进攻链，大师档最多验证四层进攻链。

当 VCF 未找到结果时，大师档会启动受控 VCT（连续威胁）证明树：活三、跳三等为攻击 OR 节点，候选防守为 AND 节点，只有所有受控防守分支都可继续形成杀棋时才认定为已证明威胁。证明树以局面 Zobrist 哈希、攻击方、节点类型和剩余攻击层数为键缓存证明/反证明结果，避免同一强制局面被重复展开。为控制手机响应时间，该求解严格限制为三层进攻、八个攻击候选和十个防守候选；一旦接近时间预算即安全退回 PVS。若没有强制战术，候选点使用开放四、断四、开放三、跳三、开放二等方向模式评分，并经主变化提示、killer 着与 history 启发重新排序，再交给迭代加深的 PVS（主变化搜索）。

搜索通过 Zobrist 哈希记录局面并复用置换表条目；每条置换表记录都带有精确值、下界或上界语义，避免将剪枝得到的界值误作精确评分。高频方向线段按三进制模式码缓存，降低重复棋型识别；候选排序结果也会在搜索树内复用。若达到截止时间，则保留上一轮完整深度获得的最佳着。四档难度均保留“立即赢/立即挡”的规则底线，区别只在搜索预算、候选宽度和低难度的可控随机性。

| 难度 | 初始时间预算 | 最大搜索深度 | 候选点上限 | 设计意图 |
|---|---:|---:|---:|---|
| 新手 | 60 ms | 1 | 6 | 反应极快，并从高分候选中留出变化 |
| 普通 | 220 ms | 2 | 9 | 能防住基础四连威胁 |
| 困难 | 700 ms | 4 | 12 | 强战术与较高对抗性 |
| 大师 | 1,500 ms | 5 | 14 | 更充分搜索，适合挑战模式 |

这些数值是合理的**初始产品配置**，不是跨设备性能承诺。正式发布前应在目标 Android 机型上测试 p95 落子时延、耗电、温升和残局题库胜率。

## 构建与安装

建议使用 Android Studio 打开项目根目录，等待依赖同步后，选择真机或模拟器执行 `Run`。项目已包含 Gradle Wrapper，也可在已安装 Android SDK 与 JDK 17 的命令行环境中执行以下命令：

```bash
./gradlew :app:assembleDebug
```

生成的调试安装包位于 `app/build/outputs/apk/debug/app-debug.apk`。这份 APK 使用调试签名，仅适合测试和内部安装；上架前应配置独立的 release 签名、应用图标、隐私说明和版本管理。

## 已验证项目质量

当前最终版本为 **2.2.0（versionCode 11）**。已在 Android API 35 构建环境、JDK 17 下成功执行 Debug 打包和单元测试。测试覆盖横向五连、自由规则下的六连、AI 对对手四连的封堵、AI 自身一手成五的优先级、断四补杀、断四必防、开放四双杀起手、对手开放四双杀的 VCF 起手封堵、中心化开局库的首手与应手、固定中盘下的受控 VCT 时间保护、棋盘右侧点击区域应映射到最近交叉点的触控回归用例、三种先手偏好对应的棋色分配、开局库不覆盖一手胜负、新手档合法落子、AI 不修改调用方棋盘，以及 9 个固定残局基准。

最终整合版另外修复了 AI 异常或非法落子时可能卡在“AI 正在计算”的状态、开局库覆盖立即胜负、局域网重连旧读线程串扰新连接，以及人机对局页先手规则文案过时等边界问题。新手档思考预算降为 30ms、候选随机范围扩大为最多 5 个，但立即成五和必须封堵仍由规则底线保证。

2.1.0 进一步将棋型识别改为三进制整数模式匹配，减少搜索节点中的短字符串分配；LAN 协议升级到 v2，增加会话标识、单调序号、消息长度与未知类型校验，并采用单线程发送队列和复用 Writer，降低重连、乱序和重复落子风险。棋盘同时补充了 TalkBack 可读的状态语义。

2.2.0 完成代码审查报告中的高收益修复：补齐 LAN 房主 Writer，保护 NSD listener 注销，使用并发房间表和发送序列，加入每秒消息限流；启动主题改为深色、启用 Edge-to-Edge 和 adjustResize；AI 异常增加日志，原生 Release 构建启用 -O2，Release 构建启用 R8/资源压缩；Material3 统一为弈境配色，AI 思考增加进度指示，节点数格式固定使用 Locale.US。

## 残局基准与外部来源

项目新增 9 个可版本化的固定战术残局，覆盖横向、纵向和对角线一手成五，横向/纵向/断四必防，以及开放四攻防。每题以明确坐标、执子方和**等价最佳着集合**编码；大师档必须通过全题，普通档必须通过其中所有一手胜负题。另设一项固定中盘时间保护测试，确认受控 VCT 在时间边界内仍返回合法落子。

这些题目是项目内维护的可复现回归基准，而非声称来自某一届赛事棋谱的原始残局。调研中确认 [Gomocup 官方赛事结果页][3] 覆盖多年赛事，2025 赛事详情页提供完整结果与开局下载入口，并公开展示 15×15 自由规则开局；其开发者页面还链接威胁空间和证明数搜索资料。[4] 由于当前环境中该官方结果包下载超时且未能逐条核验再发布许可，项目不直接打包或伪称使用其完整棋谱。后续若取得许可清晰、可稳定下载的原始棋谱，可在同一基准格式中增量导入。

[3]: https://gomocup.org/results/ "Gomocup: Results"

## 局域网对战

应用现已提供“局域网对战”模式。房主输入房间名并点击“开房并等待玩家加入”后，应用会在当前 Wi‑Fi 中发布该房间；加入方进入相同模式，点击“扫描房间”，选择发现的房间并点击“加入”即可连接。双方连接后停留在就绪页，只有房主点击“开始对局”才会开局，并随机决定双方的黑白先手；落子与暂停/继续状态通过本地 TCP 长连接实时同步。

| 能力 | 实现方式 |
|---|---|
| 房间发现 | Android NSD / DNS-SD 服务发布、扫描和解析 |
| 设备连接 | 解析房主地址与动态端口后建立本地 TCP 直连 |
| 对局同步 | 按行分隔的 JSON 消息，覆盖开始、随机棋色、落子、暂停/恢复与离开 |
| 房主规则 | 一间房只接受一名玩家；房主显式点击开始，棋色随机分配 |
| 权限 | Android 13 及以上首次进入该模式时申请“附近 Wi‑Fi 设备”权限 |

使用该功能时，双方必须连接到**同一可互通的局域网**。如果一个设备在访客 Wi‑Fi、路由器开启了 AP/客户端隔离，或两端不在同一网段，房间可能无法发现或连接。该首版采用无账号的可信局域网直连，不应在公共或不受信任网络中使用；它不提供身份验证、传输加密、断线重连或互联网穿透。

Android 官方说明，网络服务发现可发布、扫描和连接同一局域网中的服务，并将多人游戏列为其适用的点对点场景；其服务注册会广播实际端口，因此房主使用动态端口而不是硬编码端口。[1] 对 target Android 13（API 33）及更高版本的附近 Wi‑Fi 设备访问，官方要求相应的运行时权限。[2]

[1]: https://developer.android.com/develop/connectivity/wifi/use-nsd "Android Developers: Use network service discovery"
[2]: https://developer.android.com/develop/connectivity/wifi/wifi-permissions "Android Developers: Request permission to access nearby Wi-Fi devices"

## 下一阶段建议

后续可以加入连珠禁手（双三、双四、长连）和多种规则集、棋局存档与复盘、玩家统计与深色/浅色主题。联机部分可进一步实现二维码加入、断线重连、房间密码、局域网加密和互联网中继；若目标是更高竞赛级棋力，则应将当前受控 VCT 扩展为完整 VCT/证明数求解器，加入更大的开局库、增量棋型缓存和真机残局题库，并与固定基准引擎进行系统评测；不建议直接以通用对话模型替代规则与落子引擎。
